Performance of tables

How long Nihil's tables (Learn §9, §13) take to write, read, query and change, measured by bench/tables.nihil. The records are synthetic, made from a fixed pseudo-random sequence so every run has the same data, and each one has six fields in 50 bytes:

ITEM = @[#code: INT(8); name: STRING(20); category: INT(4); price: FLOAT(10); qty: INT(6); active: BOOL];

The machines: Linux, a GitHub Actions runner (AMD EPYC 7763, 4 CPUs, Ubuntu 24.04), where Nihil runs natively; and macOS, an Apple M4, where the compiler's x86-64 code is translated to ARM64. To measure your own machine, run bench/run.sh in the repository (or bench/run.sh ./nihilc1.sh from a build).

The whole table

Writing, reading and querying grow with the table. The queries are compiled into loops where they are called, so going through a million records takes less than the clock's 10 ms.

One record at a time

These cost the same with 10 000, 100 000 or 1 000 000 records: a record's place comes from its number (fixed width) or from the index on disk, so the rest of the table is never read.

Reading the numbers

  • A write by key waits for the disk. Each one calls fsync twice, once for the table and once for the index, so that a crash never leaves them out of step; that is almost all of its time, and the disk decides it (about 0.2 ms on the Linux runner, about 5 ms on the Mac's SSD). To change thousands of records at once, change them in memory and write the table once with @>>: a million records take about a second.
  • Reading by key or by number is cheap at any size, so a program can work on a large table one record at a time without loading it.
  • In memory a record is bigger than on disk: each field takes an 8-byte slot, and a text its own bytes besides. This run holds two copies of the records (the ones it made and the ones it read), about 190 bytes per record each. Reading a table needs, at its peak, two to three times the file's size.
  • One writer at a time. A table is a file, not a server: two programs writing the same table at the same moment are not coordinated.
  • The clock has a resolution of 10 ms, so the operations on one record are timed thousands at a time (20 000 reads, 300 writes) and divided. “< 10 ms” means less than one tick.

The numbers come from the run of 23 November 2026 (Nihil 4.3.1). The rules behind them are in SPEC §20.

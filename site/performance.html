Performance of tables

How long Nihil's tables (Learn §9, §13) take to write, read, query and change, measured by bench/tables.nihil, and how that compares with the same work written in C and in Go. The records are synthetic, made from a fixed pseudo-random sequence so every run has the same data, and each one has six fields in 50 bytes:

ITEM = @[#code: INT(8); name: STRING(20); category: INT(4); price: FLOAT(10); qty: INT(6); active: BOOL];

The machines: Linux, a GitHub Actions runner (Intel Xeon 6975P-C, 4 CPUs, Ubuntu 24.04), where Nihil, C and Go all run natively; and macOS, an Apple M4, where Nihil's x86-64 code is translated to ARM64. To measure your own machine, run bench/run.sh or, for the comparison, bench/compare/run.sh in the repository.

Compared with C and Go

bench/compare holds the same program in C (cc -O2) and in Go: the same records, the same text table, the same hash index on disk and the same number of disk syncs. Run with KEEP=1, the three leave byte-for-byte the same table after every change, addition and deletion. Linux, all three native, 1 000 000 records:

OperationNihilCGo

find by key (each)1.7 µs1.0 µs1.2 µs

peak memory329 MB186 MB333 MB

Nihil writes the table faster than C and Go, sorts faster than both, builds the key index as fast as they do, reads the whole table within about 10% of them and uses the memory Go uses. It takes about twice their time on one record at a time, and two to three times theirs on the queries that go over every record. The C and Go programs keep their two files open and trust that nobody else changes them; Nihil checks the table at the path on every operation (one stat), so it still sees what another program or an editor did to it.

Reading the numbers

  • A write by key waits for the disk. A change in place syncs the table; an addition or a deletion syncs the table and the index, so that a crash never leaves them out of step. That is almost all of its time, and the disk decides it (tenths of a millisecond on the Linux runner, 5 to 9 ms on the Mac's SSD, where the sync goes through the drive's cache). To change thousands of records at once, change them in memory and write the table once with @>>: a million records take under half a second.
  • Reading by key or by number is cheap at any size: the runtime keeps the files open between reads, and a lookup by key is one stat of the table and two reads, about 1 µs and 2 µs at a hundred thousand records or a million.
  • A garbage collection hardly stops the program (SPEC §12.4). From 64 MB of heap, a child process marks what is in use while the program goes on, and the sweep runs in small steps as the program allocates, so the pauses are about a millisecond, on Linux and on the Mac. With a million records in memory, timed 1 000 reads at a time, the slowest of the 20 laps takes 1.2 ms where the typical one takes 0.95 ms (Linux); before the collector worked this way, one lap in twenty took about 150 ms. C has no collector, and Go's also runs alongside the program.
  • In memory a record is bigger than on disk: each field takes an 8-byte slot, and a text its own bytes besides. This run holds two copies of the records (the ones it made and the ones it read). Reading a table needs, at its peak, two to three times the file's size.
  • Writers wait for each other. A table is a file, not a server, but every write by key takes the table's lock (a .nihil-lock file next to it), from the lookup to the last write: two programs adding records to the same table at the same moment both get theirs in. Reads take no lock.
  • On the Mac, Nihil's code and its runtime (the same as Linux's) are translated from x86-64 to ARM64, which costs most on small, frequent operations.
  • GitHub's runners are not all the same machine, and a shared server under load gives noisier numbers still. Compare numbers from the same run.
  • The clock is std:time's now_us(), in microseconds. The operations on one record are timed thousands at a time (20 000 reads, 300 writes) and divided; the reads are also timed 1 000 at a time, for the median.

The numbers come from the runs of 25 November 2026, with Nihil 4.8.0. The rules behind them are in SPEC §20.
